# 脚本

[入口](./SKILL.md) · [编排](./produce-prompt.md) · [工作流](./workflow.md) · [音色](./tone.md) · [素材](./resources.md) · [音效](./sfx.md) · [质量门](./quality.md)

本文件规定制作脚本怎么写、怎么验收。它不生成语音，也不写 Remotion 场景代码。顺序和停止条件在 [workflow.md](./workflow.md)。

核对日期：2026-11-10。

## 输入

已确认的简报：片种、主题、受众、平台、画幅、时长约束、风格、是否有出镜成片、是否商用、事实来源。

用户的经历、口感和尚未公开的产品数据，只使用用户提供的内容。可以帮他压缩句子、换成口语、排段落。不能替他编一段「我当时」的经历。

公开产品以用户给的地址、仓库或文件为准，并按 [resources.md](./resources.md) 核对。页面上没有的功能不要写进旁白。

## 三层，分开写

| 层 | 内容 | 交给后阶段的约定 |
|---|---|---|
| 旁白正文 | 实际要念出来的话 | [tone.md](./tone.md) 只收这一层。标记、屏幕说明和素材备注先去掉 |
| 屏幕文字 | 旁白不念、但画面上必须完整出现的提示、命令、示例 | 标明「仅屏幕展示」。不要压成几个要点 |
| 素材与动作 | 该段可用的截图、录屏、图表、角色动作 | 普通段可以空着，由画面阶段设计。必讲的操作、环境、示例要写明 |

旁白用口语。一段一个意思。专名、英文品牌和命令保持用户给的写法，方便后面校对字幕。

## 三种段落骨架

骨架是建议的叙事顺序，不是镜头数。短视频可以落成大约 6～8 段，这是 Smartpigai 文章里的短片起草习惯，不是长片的上限。长片按章节写，每章内部仍用该片种的顺序。不必为没有特殊要求的段落写死运镜。

| 片种 | 段落顺序 | 画面倾向 |
|---|---|---|
| 产品介绍 | 痛点 → 卖点 → 真实演示 → 行动引导 | 演示段用真实截图或录屏。卖点是一句旁白加一个能看见的依据，不把功能表铺满一屏 |
| 独立口播 | 问题 → 观点 → 例子 → 总结 | 默认没有真人出镜。观点用字幕和图形说明；例子优先用用户的材料。不要写成「主持人出现在镜头前」，除非简报里已有出镜成片 |
| 技术讲解 | 问题 → 原理 → 操作演示 → 适用边界 | 原理用图解，图解不是产品界面。操作演示用录屏或截图。边界要说出不适用于什么，避免把示例说成普遍结论 |

三种片子共用 [workflow.md](./workflow.md) 的阶段表。片种只改变这张骨架和素材的优先种类。

出镜成片已经存在时，不改骨架，给每一段加上下面的列。

## 脚本里至少有的列

写到视频工程的制作脚本里：

| 列 | 要求 |
|---|---|
| 段落 | 编号，必要时标章节 |
| 旁白正文 | 只含要念的话。没有旁白的段落写「无」 |
| 屏幕文字 | 没有则写「无」。有则注明仅屏幕展示，并保持完整 |
| 画面意图 | 观众这一段看见的那一件事。一句 |
| 素材 | 路径、待补，或「图解」。产品演示不能只写「做个界面」 |
| 备注 | 必做的动作、不可删的句子、已知的许可问题 |

有出镜成片时再加：

| 列 | 要求 |
|---|---|
| 看见谁 | 「出镜」或「B-roll 盖住出镜」。盖住时原声仍连续 |
| 成片时间 | 剪顺之后的时间。与原始素材时间分开写 |

原始素材 00:09–00:16 被剪到成片 00:05–00:12 时，两段时间都记下。脚本里写了但出镜时没说的句子，不自动补进旁白或字幕；必须讲的内容先由用户补录。

## 时长怎么处理

简报没写死秒数：按讲清楚来写。成片长度以后跟主音轨，不在本阶段用字数换算秒数。

简报写了「大约 N 秒」：按口语语速把稿控制在这个量级。合成后若差得明显，回到本文改段落，不要在画面阶段把镜头拉长来凑。

简报写了「必须正好 N 秒」：在脚本里标成硬约束，连同片头片尾一起算。后面若要用时间拉伸去卡秒，先问用户。那会改变声音。

## 画面意图的限度

写意图，不写组件。可以写「标题出现后，切到设置页的录屏」。不要写一段 React。

同一支片子先定背景、字体和信息层级。转场和元素移动要帮助这句话被看懂。不要要求每个元素都飞入飞出。

产品界面：写要用的真实画面。只有在 [resources.md](./resources.md) 允许代码绘制时，才把该段标成「代码绘制界面」，并写明用户已接受。

图解、示意图、结构图可以是后来用代码做的，它们不是产品截图。在素材列写「图解」，不要标成截图。

## 验收

交给用户确认前自行检查：

- 旁白层没有标记、没有「画面：」之类的说明。
- 必讲的操作、命令和示例在屏幕文字或旁白里完整保留。
- 产品介绍和技术讲解的演示段，每段都有真实素材或明确缺口。缺口没有被偷偷改成代码绘制。
- 独立口播没有假设一个并未提供的出镜人物。
- 没有用户没提供的经历、销量和性能数字。
- 出镜分支的「看见谁」和成片时间没有和原始素材时间混在一起。
- 片种骨架的四步都能在段落里找到。某一步确实不需要时，在备注里写原因，而不是悄悄跳过。

用户确认的是这一版制作脚本。之后旁白正文有改动，就要重新确认受影响的段落，并按 [workflow.md](./workflow.md) 回到主音轨。

## 失败时

| 现象 | 处理 |
|---|---|
| 事实不够，稿子只能靠猜 | 停在本阶段，列出缺的事实。不往下配音 |
| 用户否定结构 | 只改他指出的段落，再给一次脚本。不带着被否定的稿去合成 |
| 演示段没有素材，用户也拒绝代码绘制 | 该段留空，不进入画面。向用户要截图或录屏 |
| 稿子确认后又改了口播句子 | 作废受影响的音轨和 SRT，从 [tone.md](./tone.md) 重做 |
